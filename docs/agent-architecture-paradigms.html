导读：为什么这四个概念常被混为一谈

这四个词描述的是智能体系统里不同抽象层次的东西，不是四个互斥的竞品。把它们放在一根「控制权 / 复杂度」轴上会更清楚：

Loop（单体循环） → Subagents（委派子任务） → Multi-Agent（多体协作） ↕ Graph（编排底座）

Loop 是最小执行单元；Subagents 是把 Loop 当工具委派出去；Multi-Agent 是多个 Loop 协作；Graph 是把上述结构显式编排、加上状态与持久化的底层框架。

本报告先讲清它们共享的基础（增强型 LLM），再逐个拆解四种范式的理论架构、适用场景与落地所需条件，最后给出横向对比表和选型决策树。核心判断来自 Anthropic「一切从最简单方案开始，只在可证明有收益时才增加复杂度」的工程原则。

共同基础：增强型 LLM 与「Agent vs Workflow」

基础构件：Augmented LLM

四种范式的最小单元都是一个被检索（Retrieval）、工具（Tools）、记忆（Memory）增强过的 LLM。模型自己生成检索查询、选择工具、决定保留什么信息。所有更复杂的结构都是在这个构件上堆叠出来的。

关键区分：Workflow 与 Agent

Workflow（工作流）

LLM 与工具通过预先写好的代码路径被编排。路径确定、可预测、可复现。

典型模式：Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer。

Agent（智能体）

LLM 动态决定自己的流程和工具调用，在循环中根据环境反馈自主推进，直到完成或触发停止条件。

本质就是「LLM 在循环里基于环境反馈使用工具」。

Andrew Ng 的视角值得借鉴：与其纠结「它是不是一个 Agent」（名词、二元判断），不如问「它有多 agentic」（形容词、程度判断）。生产环境里的系统几乎都是 workflow 与 agent 的混合体。
贯穿全篇的核心难点（LangChain 观点）：构建可靠智能体系统，最难的不是拼装组件，而是确保 LLM 在每一步都拿到恰当的上下文——既要控制进入 LLM 的确切内容，也要跑对生成这些内容的步骤。Loop / Subagents / Multi-Agent / Graph 本质都是「管理上下文」的不同手段。

1Loop Engineering（循环工程）

最小、最基础的智能体范式：一个 LLM 在 while 循环里反复「思考 → 调用工具 → 观察结果」，直到解决问题。

理论架构

一个 agent 由三个参数决定：要用的模型、系统提示（指令）、可用工具集。运行方式是：

while 未触发停止条件:
    response = LLM(model, instructions, messages, tools)
    if response 调用了工具:
        observation = 执行工具()
        messages += observation      # 把反馈喂回上下文
    else:
        return response              # LLM 不再调用工具 → 结束
Thought 思考 → Action 调用工具 → Observation 观察 ↺ （循环 N 次）

ReAct 模板：Thought / Action / Observation 反复循环

循环工程的核心手法

  • ReAct：把推理（reasoning）和行动（acting）交织，让模型在自然语言里边想边做。
  • Reflection / Reflexion（自我反思）：每轮结束用启发式判断轨迹是否低效或出现幻觉（例如连续重复同一动作），把反思写入工作记忆指导下一轮。
  • Evaluator-Optimizer（评估-优化循环）：一个 LLM 生成、另一个 LLM 评估并给反馈，迭代精修。
  • 停止条件工程：最大迭代次数、ground-truth 校验、人类检查点（human-in-the-loop），防止无限循环和错误累积。

使用场景

适用开放式问题、无法预先确定步骤数、无法硬编码固定路径的任务。典型如：编码 agent（SWE-bench）、computer use、需要多轮搜索精修的检索任务。

不适用步骤固定、可清晰分解的任务——那种用 workflow（prompt chaining / routing）更便宜、更快、更可预测。

所需条件

模型能力
足够强的推理、规划、可靠工具调用、错误恢复能力。这是循环能自主推进的前提。
工具与接口（ACI）
精心设计的工具集和文档——「Agent-Computer Interface」和人机界面同等重要。工具描述差会把 agent 带偏。
环境反馈（ground truth）
每一步都要能从环境拿到真实反馈（工具结果、代码执行结果）来评估进度。
护栏
沙箱环境、最大迭代次数、检查点，控制成本与失控风险。
信任门槛
因为模型会自主跑很多轮，你必须对它的决策有一定信任，并在受信环境中运行。

2Subagents（子智能体）

把一个独立的 agent 循环封装成「可被主 agent 调用的能力」，用于委派带独立上下文窗口的子任务。它是 Multi-Agent 的具体实现单元。

理论架构：Orchestrator-Worker（编排者-工人）

Lead / Orchestrator 主智能体
↙↓↘
Subagent A Subagent B Subagent C

主 agent 拆解任务并动态委派；子 agent 各自带独立上下文并行探索，把压缩后的结果回传给主 agent 综合。

为什么子智能体有价值

  • 上下文压缩与隔离：搜索的本质是压缩。每个子 agent 用自己独立的上下文窗口探索问题的一个侧面，把最重要的 token 蒸馏后回传，避免主上下文被撑爆（超过 200K 会被截断）。
  • 关注点分离：每个子 agent 有独立的工具、提示和探索轨迹，减少路径依赖，能做彻底、独立的调查。
  • 并行扩展算力：多个子 agent 同时跑 = 把 token 预算分散到多个并行推理通道。

使用场景

适用无法预知子任务数量的复杂任务（Orchestrator-Worker 与 Parallelization 的关键差别就在于子任务是动态决定还是预定义）。如：需要改动多个文件的编码任务、需要从多来源收集分析信息的搜索任务。

所需条件

清晰的委派指令
每个子 agent 需要：明确目标、输出格式、工具/来源指引、任务边界。指令模糊会导致子 agent 重复劳动或留下空白（Anthropic 早期就踩过多个子 agent 重复搜同一主题的坑）。
努力度分级规则
在提示里嵌入「简单事实查证用 1 个 agent + 3-10 次工具调用；复杂研究用 10+ 子 agent」这样的资源分配规则，防止对简单问题过度投入。
持久化/记忆
主 agent 需把计划存入 Memory，以防上下文截断时丢失。
结果综合机制
主 agent 要能判断信息是否足够、是否需要再派子 agent，并最终综合（可能再接一个专门的引用/校验 agent）。

3Multi-Agent Systems（多智能体系统）

多个 agent（各自是「在循环里自主用工具的 LLM」）协同工作的系统。Subagents 是它的实现单元，Orchestrator-Worker 是它最常见的拓扑。

理论架构与量化收益

Anthropic 的 Research 系统采用 Opus 4 主 agent + Sonnet 4 子 agent 的多智能体架构，在内部研究评测上比单体 Opus 4 高出 90.2%。其关键发现：

  • 在 BrowseComp 评测里，token 用量单独就解释了 80% 的性能方差；再加上工具调用次数和模型选择，三者共解释 95%。
  • 多智能体系统之所以有效，主要是因为它能把足够多的 token 投进问题——通过分散到多个独立上下文窗口来扩展并行推理容量。
  • 擅长广度优先（breadth-first）查询：同时追多个独立方向。例如「找出 S&P 500 里所有 IT 公司的董事会成员」，多智能体分解成子任务成功，单体因串行搜索太慢而失败。
代价必须正视：多智能体系统消耗 token 极快——普通 agent 约是聊天的 4×，多智能体系统约是聊天的 15×。因此只对「价值足够高、值得为性能付费」的任务才划算。

使用场景

适用(1) 价值高且高度可并行化的任务；(2) 信息量超过单个上下文窗口；(3) 需要对接大量复杂工具。典型：深度研究、广度信息聚合。

不适用(1) 所有 agent 需共享同一上下文的任务；(2) agent 之间依赖很多、需实时协调的任务。大多数编码任务就属于此类——真正可并行的子任务少，而当前 LLM 还不擅长实时相互协调与委派。

所需条件

协调与提示工程
协调复杂度随 agent 数量快速增长。提示是主要调控杠杆——要教会编排者如何委派、如何按查询复杂度分配努力度。
面向结果的评估
传统「输入 X → 固定路径 Y → 输出 Z」的评估失效。多智能体即使起点相同也会走不同的有效路径，必须用评判最终结果是否正确 + 过程是否合理的灵活评估（可用 LLM-as-judge，先用小样本快速迭代）。
可观测性
需要能一步步观察 agent 行为的仿真/追踪能力，才能发现失败模式并快速迭代。
经济性论证
任务价值必须能覆盖约 15× 的 token 成本。
工具设计
面对大量 MCP 工具，需给 agent 明确的工具选择启发式；坏的工具描述会把 agent 带向完全错误的路径。

4Graph Engineering（图工程）

与前三者不同，图工程是编排底座层：把智能体系统显式建模为「节点 + 边」的图，用来精确控制流程、状态、持久化和人机交互。代表是 LangGraph。

理论架构

LangGraph 是事件驱动的编排框架，把智能体系统表示为：

START → Node A（工作单元） → 条件边（动态路由） → Node B ↺ Node A（可回环）
  • 节点（Nodes）= 工作单元，本质就是普通 Python/TypeScript 函数（内部是命令式代码）。
  • 边（Edges）= 状态转移，可以是固定边或条件边。所以图的结构是声明式的，但路径可以完全动态。
  • 因此 LangGraph 是声明式 + 命令式的混合体：结构声明式，节点逻辑命令式，还提供 functional API 与底层事件驱动 API。

图工程提供的关键能力

  • 内置持久化层：带来容错、短期记忆、长期记忆。
  • Human-in-the-loop / Human-on-the-loop：interrupt（中断）、approve（审批）、resume（恢复）、time travel（时间旅行/回溯）。
  • 流式输出：token 级、节点更新级、任意事件级的 streaming。
  • 可观测性：与 LangSmith 集成做调试、评估、追踪。
「高天花板 + 低门槛」定位：纯 workflow 框架天花板高但门槛也高（要自己写很多逻辑）；纯 agent 抽象门槛低但天花板低（很快就不够用）。LangGraph 想同时拥有二者——既有开箱即用的 agent 抽象（低门槛），又有底层能力支撑高级用例（高天花板）。它能在「可预测 ↔ 自主性（agency）」曲线上的任意点构建应用。

使用场景

适用(1) 需要 workflow 与 agent 混合、且要在「可预测性」和「自主性」之间精确调档的生产系统；(2) 因用户信任/合规原因需要高可预测性；(3) 需要持久化、人工审批、断点续跑、可观测性的长周期任务；(4) 需要精确控制每一步喂给 LLM 的上下文。

谨慎Anthropic 提醒：框架会引入抽象层，可能遮蔽底层提示与响应、增加调试难度，也容易诱使你在更简单方案够用时过度加复杂度。建议先直接用 LLM API，若用框架务必理解其底层实现。

所需条件

状态建模能力
要能把任务显式建模为节点、边、共享状态（state）。这是图工程的核心心智负担。
对上下文的精确控制诉求
图工程的价值正是「精确决定数据如何流动、每步喂什么上下文」，如果你不需要这种控制，用轻量 agent 抽象即可。
基础设施
持久化后端（支撑记忆/续跑）、可观测性平台（如 LangSmith）。
对框架底层的理解
用框架就要理解其抽象之下发生了什么，否则「对底层的错误假设」是常见错误来源。

选型决策树

遵循 Anthropic 原则：从最简单方案开始，只在可证明有收益时才加复杂度。

  1. 单次 LLM 调用（+检索+示例）能解决吗？ → 能，就别上智能体。
  2. 任务能清晰拆成固定步骤吗？ → 能，用 Workflow（prompt chaining / routing / parallelization），可预测又便宜。
  3. 步骤数无法预知、需要模型自主决策吗？ → 用 Loop / Agent。备好强模型、好工具、环境反馈和护栏。
  4. 任务能拆成多个动态、可并行的子任务吗？子任务数无法预知？ → 用 Subagents（Orchestrator-Worker），给足清晰委派指令。
  5. 是高价值、广度优先、信息超单一上下文窗口的任务，且能承受 ~15× token？ → 上 Multi-Agent，配面向结果的评估与可观测性。
  6. 需要在可预测性/自主性间精确调档、要持久化、人工审批、断点续跑、生产级可观测性？ → 用 Graph Engineering（LangGraph） 作为编排底座承载上述结构。
三条贯穿始终的原则（Anthropic）：保持设计简单；优先透明（显式展示 agent 的规划步骤）；精心打磨 Agent-Computer Interface（工具文档与测试）。框架能帮你快速起步，但走向生产时不要怕削减抽象层、回到基础构件。
